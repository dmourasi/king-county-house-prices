Item 3 · Estratégia de Deploy

Como este modelo iria pra produção

Este desenho não foi implementado — é o que eu proporia para colocar o modelo (XGBoost, item 2.1, implementação Python) em produção, dimensionado para o problema real: volume de tráfego provavelmente baixo, e um modelo que já sei, pelos meus próprios testes de generalização (item 2.2), onde é mais fraco.

Fluxo principal ao centro (cliente → API → feature pipeline → modelo → flag de confiança → resposta); observabilidade e reentreino à esquerda, fechando o ciclo de volta ao Model Registry.

As camadas, e por que decidi cada uma assim

1 · Feature pipeline

A parte que mais me preocupa

O maior risco de bug em produção não é o modelo em si, é a lógica de feature engineering (tem_porao, idade_casa, reformado) ser reescrita de um jeito ligeiramente diferente no serviço de produção do que no notebook de treino (training-serving skew). Por isso encapsularia essa lógica numa única função/pacote compartilhado entre os dois lados, em vez de reimplementada duas vezes.

2 · API

A flag não é genérica

Além do preço (revertido de log_price para dólar) e do intervalo de confiança (mesma lógica de bootstrap do item 2.2), a API devolve uma flag de confiança baixa quando o zipcode do imóvel não estiver entre os vistos no treino — tradução direta do achado mais importante da generalização: o modelo erra cerca de 20% mais em CEPs novos.

3 · Infraestrutura

Proporcional ao problema, não ao que impressiona

Container com o modelo carregado do Model Registry na inicialização, atrás de um serviço gerenciado simples (Cloud Run / ECS Fargate) com autoscaling básico. Não vejo justificativa para Kubernetes aqui — o volume (~21 mil imóveis históricos, uma predição por vez) não pede essa complexidade operacional. O modelo XGBoost salvo tem ~0,4MB (contra ~25MB de uma Random Forest equivalente) — cold start do container praticamente não é afetado pelo carregamento do modelo.

4 · Versionamento de modelo

Rollback imediato, não reconstrução

Cada modelo é salvo com um identificador (data + hash do pipeline de treino + métricas das três estratégias de validação do item 2.2). O "modelo em produção" é um ponteiro/alias no registro — trocar de modelo é trocar o alias.

5 · Monitoramento

Métricas que eu já sei que importam

% de previsões em CEPs fora do treino, distribuição das previsões vs. treino, e erro real vs. previsto assim que a venda é confirmada — comparado contra o intervalo de confiança já calculado, não um limiar arbitrário.

Sobre a versão RO projeto também tem uma implementação alternativa em R (Random Forest, `analysis-r/02-1_modelagem.qmd`) — mesma arquitetura proposta aqui, trocando FastAPI/joblib por plumber/`.rds`. Diferenças específicas em analysis-python/03_estrategia_deploy.md.
